# Firestore audit — opportunities

Created for the Opportunity feature security-rule review.

## Data model

`opportunities/{id}` is a public request. It contains only the public contact
number deliberately supplied by the request author, task category, short task
description, coarse location (city, neighbourhood, state), and optional urgency
classification (`normal`, `soon`, or `urgent`). It does not copy email, a full
address, private profile data or member-verification fields.

The immutable ownership fields are `authorId`, `authorName`,
`authorWhatsApp`, and `createdAt`. Request authors may change status and answer
the 20-day follow-up. Admins retain moderation access.

## Access and queries

- Public/professional feed: `status == active`, ordered newest first; optional
  category and state equality filters. The client may sort active records by
  urgency after fetching; no additional Firestore query shape is required.
- Author history: `authorId == auth.uid`, ordered newest first.
- Create/update/delete: authenticated owner, not blocked; schema and immutable
  fields checked by `isValidOpportunity` and `keepsOpportunityIdentity`.
- Personal notifications: `users/{uid}/notifications/{id}`. Only the owner may
  read and mark the `read` field; creation is denied to browser clients and is
  performed only by trusted Cloud Functions using the Admin SDK.

## Provider search index

Public profiles now store a bounded `searchTokens` list derived only from
already-public profile fields (name, service category/type, company and coarse
location). Searches always use Firestore equality filters plus one indexed
token and fetch at most 60 candidates; category, state and remaining words are
then checked in memory. This avoids reading the complete provider collection.
Existing profiles must be refreshed with `npm run backfill:public-profiles`
after the rules and indexes are deployed.

## Sensitive data boundary

Religious verification inputs (ward, baptism year and membership duration) and
precise location (address, number, neighbourhood and complement) stay only in
the owner-only `users/{uid}` document. The public profile does not contain
those fields or religious verification status. A member may explicitly opt in
to publishing only `publicCity` and `publicState`; search tokens use no more
precise location data.

## Community recommendations

Each recommendation is a private-to-the-recommender record at
`public_profiles/{professionalId}/recommendations/{recommenderId}`. The public
profile exposes only `recommendationCount`, never who recommended the person.
Rules require the recommendation document and its counter change to occur in
the same transaction, prevent self-recommendation, and permit at most one
active recommendation per member and professional.

## Identified ratings

New ratings store `fromId` and the author-name snapshot. Firestore Rules bind
the identifier to `request.auth.uid` and require the submitted name to match
the private profile name, preventing attribution spoofing. The author name is
intentionally public with the rating; historical anonymous records remain so.

## Trusted automation

`notifyMatchingProfessionals` queries private user profiles only in the trusted
server runtime, matching `isProvider`, `category`, and `businessState`, then
creates deterministic per-recipient notification documents. The scheduled
`maintainOpportunities` job sends one 20-day follow-up and changes expired
requests to `expired` after their `expiresAt` timestamp.

## Automation boundary

The web client also hides records whose `expiresAt` has passed as a fallback.
The trusted scheduled backend remains the source of truth for the 30-day
expiration; Firestore Security Rules cannot run jobs or mutate documents on
their own.
